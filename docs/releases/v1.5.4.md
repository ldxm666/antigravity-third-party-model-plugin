# v1.5.4 · 失败明确结束 / Visible provider failures

## 中文

- 修复第三方模型上游超时后被原生执行器连续隐藏重试的问题。现在 API 错误结束当前执行，显示原生错误及手动重试入口。Google 模型的重试行为、输出截断后的原生续写策略不变。
- 修复 Gemini 原生适配器丢失思考签名、只有签名的片段和工具调用 ID 的问题，并对提前返回响应头的 JSON 回退保持超时保护。
- 思考档位覆盖保留调用者显式设置的 `includeThoughts`，不强制开启或关闭思考摘要。
- 240 项本地检查通过：45 单元 / HTTP、156 协议、39 全新配置；Windows 隔离安装、重复升级及字节一致回滚另行验证。
- 真实应用失败路径验证：本地模拟上游 HTTP 504，仅一次请求，执行结束并显示原生错误。真实应用文件生成验证：一个已配置的第三方模型在约 80 秒完成 SVG 动画 HTML、文件写入和最终回复；这不保证其他提供商或任务的速度。

**边界：** 首响应默认等待上限为 180 秒，流空闲为 120 秒。该修复避免错误被连续隐藏，不代表修复了提供商服务。若无首响应，请核对上游状态或选择其他已配置的模型。

升级应用补丁后通常需从托盘完整退出再正常打开一次；桥核心更新使用 `restart-bridge.cmd`。保留原有提供商配置，请勿分享配置、API Key、原始请求或账户截图。

## English

- Third-party API failures now end the current execution with native error and manual retry controls instead of hidden repeated requests. Google retries and native output-truncation recovery remain unchanged.
- Preserve original Gemini parts, thought signatures, signature-only chunks and function-call IDs. Keep deadlines active for JSON fallback bodies after early response headers.
- Preserve an explicitly requested `includeThoughts` setting when applying a reasoning override.
- 240 local checks passed (45 unit/HTTP, 156 protocol, 39 fresh-configuration), plus isolated Windows install, upgrade and byte-exact rollback validation.
- Native failure-path acceptance verified one local upstream request and a visible terminal error. A live third-party model also completed an SVG animation HTML, file write and final reply in about 80 seconds. This is evidence for that run, not a provider latency guarantee.

The default first-response deadline is 180 seconds and stream-idle deadline is 120 seconds. These changes surface failures; they cannot restore an unresponsive provider. Fully quit/reopen the application after a normal patch upgrade and use `restart-bridge.cmd` for bridge-core changes. Existing provider settings are retained.
